# Adaptive DPI Strategy Layer

Этот документ описывает первый шаг Chameleon Protocol 0.3.0.

## Зачем нужен отдельный слой

У разных сетей один и тот же способ передачи ведёт себя по-разному. Домашний Wi-Fi,
мобильная сеть и публичная сеть могут использовать разные фильтры, NAT и ограничения.
Поэтому Chameleon не должен держать одну глобальную стратегию.

Новый слой хранит опыт по ключу:

```text
network + destination + traffic class -> strategy statistics
```

Пример:

```text
mobile-a + video.example:443 + streaming -> split-early
wifi-home + video.example:443 + streaming -> direct
wifi-home + bank.example:443 + web -> direct
```

Это важно для совместимости: если обычное соединение уже работает, Chameleon его
не меняет.

## Что взято из идей zapret / ByeDPI

Мы не копируем их код целиком. Берём архитектурные идеи:

- несколько стратегий вместо одного фиксированного режима;
- дешёвая стратегия применяется первой;
- более сложная стратегия включается только после ошибки;
- результат запоминается и повторно используется в той же сетевой ситуации;
- обработка может быть локальным proxy/sidecar, а не отдельным системным VPN;
- packet-level backend отделён от обычного userspace режима.

Такой подход позволяет не привязывать весь Chameleon к Linux netfilter и не
делать root обязательным для Windows/Android.

## Текущие стратегии

### direct

Обычная передача без изменений. Имеет минимальную стоимость и всегда является
первым вариантом без истории.

### split-early

Разбивает первый участок передаваемых данных на несколько последовательных
записей. Это userspace-вариант, который можно использовать внутри локального
proxy или embedded-клиента.

Важно: отдельные `Write()` не гарантируют конкретную TCP-сегментацию на проводе.
Поэтому этот режим считается лёгкой попыткой, а не заменой packet-level backend.

### paced-split

То же разбиение, но с небольшой паузой между фрагментами. Стоит дороже по
задержке, поэтому learner выбирает его только когда более дешёвые варианты хуже.

### fake-then-split / disorder-split

Эти стратегии пока объявлены только как packet-control capabilities.

Они не исполняются обычным Go writer, потому что для корректного поведения нужны
платформенные механизмы управления пакетами. Generic executor возвращает
`ErrRequiresPacketControl`, а не делает вид, что стратегия сработала.

В будущем:

- Linux/router: отдельный backend через packet queue / raw packet control;
- Windows: отдельный backend с подходящим packet interception API;
- Android без root: userspace proxy / VpnService bridge без raw packet tricks.

## Как работает обучение

Для каждой стратегии сохраняются:

- число попыток;
- успешные и неуспешные попытки;
- текущая серия ошибок;
- средняя задержка;
- средняя пропускная способность;
- время последнего успеха и ошибки.

Выбор детерминированный и дешёвый. Никакой нейросети и облачного сервиса нет.

Базовая логика:

1. если истории нет — используем самый дешёвый вариант, обычно `direct`;
2. если он стабильно падает — непроверенная следующая стратегия получает шанс;
3. успешный вариант получает высокий score;
4. дорогие стратегии имеют cost penalty;
5. история одной сети не переносится автоматически на другую сеть.

## Почему DPI-обход нельзя сделать только на удалённом сервере

Если фильтр находится между клиентом и сервером, изменение, которое должно
повлиять на классификацию исходящего ClientHello/TCP/UDP, должно происходить до
этого фильтра. Поэтому часть zapret/ByeDPI-подобных идей обязательно живёт:

- на клиенте;
- на домашнем/офисном шлюзе;
- либо в локальном sidecar/proxy.

Удалённый Chameleon server остаётся endpoint/carrier server и не требует установки
дополнительного коммерческого сервиса.

## Цель следующего этапа

После стабилизации Strategy Engine:

1. добавить NetworkContext detector;
2. добавить destination/traffic classifier;
3. связать выбор DPI strategy с выбором carrier;
4. реализовать локальный proxy mode;
5. добавить Linux packet backend как optional capability;
6. сохранить Tailscale/DERP как один из fallback carriers, а не как основу всей схемы.

Главный принцип: **не применять обход там, где сеть уже работает нормально**.
Это уменьшает overhead, сохраняет скорость и снижает число конфликтов с банками,
играми, CDN и другими чувствительными сервисами.
